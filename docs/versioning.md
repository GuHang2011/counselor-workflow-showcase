# 版本管理

从 v1.1.0 起，每次交付按版本号更新。根目录 `VERSION` 是唯一产品版本来源，内容为不带 v 的 `主版本.次版本.修订号`，如 `1.1.0`。

| 变化 | 下一版本示例 |
| --- | --- |
| 修复缺陷、安全补丁、兼容的样式或说明更新 | 1.1.0 → 1.1.1 |
| 增加兼容的新功能或明显改进工作流程 | 1.1.1 → 1.2.0 |
| 不兼容 API、数据迁移或部署方式变更 | 1.2.0 → 2.0.0 |

本规则管理产品交付。历史 package.json / Maven 组件版本是构建元数据，不能据 JAR 文件名判断系统产品版本。为保持已验收二进制一致，本轮不重写这些组件版本。

## 每次发布

1. 递增 `VERSION`，在 `CHANGELOG.md` 顶部增加对应版本，创建 `docs/releases/v版本号.md`，记录变化、验证、已知问题及迁移/回退方法。
2. 运行 `python scripts/check_version.py`。公开仓库 CI 还会与前一提交的 VERSION 比较，拒绝不递增的更新或不匹配的标签。
3. 代码变更后重新构建和验收；验收必须绑定待发布前后端的校验值。仅归档说明和版本管理的变更可复用未变化、校验一致的已验收产物。
4. 在完整本地项目运行 `./deploy/package-version.ps1 -WebDirectory '本次已验收的生产目录'`，生成 `deploy/release-v版本号.zip` 与校验文件。包内包括 VERSION、更新日志、版本清单和验收摘要。脚本不会覆盖旧包。
5. GitHub 提交、标签 `v版本号`、Release 标题和文档版本保持一致。标签只能新建，不强制修改旧标签；发布后若发现错误，修复并递增版本。
6. 上线前备份并保留旧发布目录。涉及数据迁移时先演练恢复，不能只回滚程序文件。

## 历史与公开范围

日期命名的历史包保留，不重新贴标签、不覆盖旧证据。公开 GitHub 仓库是展示与审阅仓库，包含代码摘录及脱敏证据；完整部署包在本地交付。不得把数据库、真实附件、密钥、会话令牌或原始测试日志上传到公开仓库。
